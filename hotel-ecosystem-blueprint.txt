OAK HOTEL HIMS - ECOSYSTEM BLUEPRINT

1. VISION
Sistem hotel terintegrasi yang mengelola seluruh aktivitas dari sales, reservation, guest CRM, PMS, front office, room, housekeeping, maintenance, POS/F&B, inventory, procurement, AP/AR, payment, accounting, HR, payroll, CRM, marketing, analytics, hingga owner reporting.

Tujuan utama:
- 1 hotel = 1 source of truth per domain
- 1 transaction flow
- 1 correlation ID
- 1 audit trail
- 1 financial ledger yang ter-reconcile
- tidak ada double booking, double payment, duplicate event, lost event

2. PRINCIPLE ARCHITECTURE
- Domain-driven design
- Modular monolith first, microservice ready later
- Event-driven via transactional outbox
- Strong transactional boundaries per domain
- Audit-first & immutable financial ledger
- API-first integration for web, mobile, OTA, payment gateway, channel manager

3. DOMAIN OWNERSHIP
Guest CRM: guest profile, dedupe, loyalty, communication preference, privacy
Reservation / PMS: reservation, stay lifecycle, room assignment, no-show, check-in/out
Availability Engine: sellable room inventory, room block, group block, OTA availability sync
Folio & Billing: folio charges, split bill, adjustments, discount, routing
Payment: payment state, auth/capture/refund, allocation
Housekeeping: room task lifecycle, inspection, deep clean, DND/MUR, room readiness
Maintenance: assets, tickets, technician assignment, SLA, downtime
POS/F&B: order, table, menu, modifier, split bill, kitchen orders, COGS
Inventory: stock ledger, warehouse, recipes, BOM, consumption, waste
Procurement: PR, PO, GRN, invoice, 3-way match
AP / AR: supplier invoice, customer invoice, aging, collections, credit hold
Accounting / GL: journals, ledger, trial balance, financial period close
HR / Payroll: employee master, attendance, overtime, payroll, bank transfer
Analytics / BI: operational BI, financial BI, owner dashboard, forecasting

4. DATA PERSISTENCE MODEL
Use structured ownership:
- each domain owns its own table set and own write authority
- cross-domain read is allowed via events or dedicated read models
- no domain mutates another domain table directly

Recommended database layout:
- 1 primary PostgreSQL instance for MVP
- separate schema or logical database per domain if scaling later
- Redis for lock TTL, cache, queue state, rate limit
- optional Kafka/RabbitMQ for event bus

6. TRANSACTIONAL RULES
- Every write must be protected by DB transaction
- Every domain change must append audit_log
- Every important change must emit outbox event in same transaction
- Every event must be idempotent on consumer side
- Every external request must be idempotent by key
- Retry is exponential backoff with jitter
- Dead-letter queue for failed event processing

8. API / INTERFACE STRATEGY
Base REST rules:
- /api/v1/... for versioned api
- standard response envelope: { status, data, error, correlation_id }
- auth: JWT / OAuth2 / API key / HMAC signature for webhooks
- rate limit on public and third-party APIs
- OpenAPI for all APIs

10. SECURITY RULES
- Secret manager for payment gateways and OTA credentials
- Encryption for PII / KTP / passport / payroll info
- Masking of sensitive fields in UI and logs
- RBAC roles: owner, GM, finance, FO manager, FO staff, HK supervisor, HK staff, kitchen, restaurant, purchasing, HR, payroll, sales, engineer, auditor
- ABAC: department, outlet, amount, time, device, transaction type
- Maker-checker for critical operations: refund, manual journal, payroll approval, stock adjustment, period reopen

11. NON-FUNCTIONAL REQUIREMENTS
- RPO and RTO defined per critical domain
- Backup + restore tested regularly
- Health checks and alerts for DB, app, queue, OTA, gateway
- Distributed tracing for all external requests
- Rate limiting and retry strategy
- Circuit breaker for external providers
- Completed UAT for FO, Finance, HK, F&B, HR

15. RISKS TO WATCH
- double booking under concurrency
- lost events and duplicate processing
- payment double capture
- unbalanced GL entries
- stale inventory due to designed use of consumption and receipts
- mismatch between room physical state and sellable availability

16. SUCCESS CRITERIA
- no double booking in concurrency test
- one reservation per room/date capacity when stock is full
- idempotency prevents duplicate processing
- accounting entries balance
- outbox publishes events reliably
- nightly snapshot produces correct occupancy, ADR, RevPAR
- end-to-end check-in to folio to payment to checkout works
